# Interview prep

1. Ask who is in the room if you cannot tell from context. The same story is told differently to each seat.
2. Find the atoms: from `skills`, take the roles that hold the role's tags (the `# Roles` table says which fragment holds which atom), read only those `facts - <role id>` fragments, and take the atoms with a `star` block or a clear result. Read the job's `jd` document (Drive, `jobs/<slug>/`) for the role's emphasis.
3. Build STAR points (Situation, Task, Action, Result) from the atom and its `star` block. If `s` or `t` is empty, **ask the person** for the missing context.
   Never invent a Situation or Task to make a Result sound better; an invented backstory is the first thing a follow-up question breaks. Save what they tell you into the atom's `star` (a fragment write, then rebuild the index).
4. One telling per audience:
   - **CTO / VP Engineering:** architecture decisions, scale, risk tradeoffs, business impact. Skip tool mechanics.
   - **IT manager / hiring manager:** process gains, ticket and incident reduction, cross-team work, what got easier for the team.
   - **Recruiter / HR:** the outcome in plain language and the working-with-people angle. No depth on tools.
   - **Peer / technical panel:** exact tools, configuration decisions, troubleshooting steps. The one audience where mechanics are welcome.
5. Keep each point to a few sentences of talking notes, not a script. If the real title differs from the resume framing (see `profile` and `rules`), remind them to state the real title when asked.

For screening questions ("why us", "a time you handled a difficult stakeholder") answer in their voice from real atoms, and say so when there is not enough on file to answer well.
